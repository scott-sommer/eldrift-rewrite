## Continuous miner behavior
minerStep provides a continuous station-work policy through narrow ports: spawning wait, danger-first retreat, explicit missing-target failure, assignment wait, shared movement travel, infrastructure establishment, maintenance, full-store handoff and harvesting. Arrival and accepted work remain running, rather than completing the mining task. Each step selects one work action; a zero-CARRY miner is allowed to harvest without a store.
Energy and mineral readiness are separate functions: energy depletion waits for regeneration; minerals additionally require an active extractor and respect its cooldown. These are observation-driven handlers, not game-global readers. Establishment/handoff mechanics and readiness observations still need native composition; retreat destinations/risk are caller policy.
Validation: 247 tests passed in 2.74s; quality/Lizard passed with 99 production files and zero violations. Tests cover danger priority, unseen versus missing targets, action selection, zero-CARRY handling, depletion, missing extractor and cooldown. No engine station-production evidence yet.

Native infrastructure observation filters sinks by actual range, link ownership/activity and resource capacity; it discovers existing adjacent container construction sites and damaged reachable station structures for establishment/maintenance. The caller supplies the reservation result, safety/retreat policy and route policy. This adapter does not allocate population, create construction sites or flush movement independently.

## Throughput-aware capacity planning
planMiningCapacity accepts live and queued production rates separately, counts mixed worker sizes rather than assuming equal bodies, preserves caller queue priority, cancels excess queued demand and requests only the remaining productive capacity. Access tiles cap concurrent workers; the result exposes throughput that cannot be covered at the proposed replacement rate. One final worker may exceed the exact rate because workers are indivisible. Existing live workers are never silently retired by this planner.
Energy regeneration retains demand. Unsafe/unassessed stations and depleted/mining-without-extractor mineral stations admit no new capacity. The caller must exclude workers due for replacement, supply measured/effective production rates (including damage/boost/cooldown policy), and supply queued requests in priority order. This is the decision mechanism; durable queue application and colony integration remain outstanding, so it does not yet prove engine source saturation.
Validation: npm run quality passed (106 production files; zero Lizard violations); npm test passed 257 tests in 2.79s. Tests cover mixed capacities, overcapacity cancellation, queued priority, tile-limited shortfall, damaged workers, regeneration, unsafe/depleted stations and invalid inputs. Engine suite was not rerun for this pure planning addition.

## Durable mining demand
applyMiningDemand connects capacity planning to the existing spawn queue and reserved identities. Its stable owner includes station room and identity, while spawning occurs in the configured home room. Live workers retain explicit effective production rates; queued body rates use an injected estimator. Spawned names are removed from pending capacity before counting spawning workers, avoiding double counting. Retirement uses replacement body spawn time plus configured travel and margin; early replacements may stage while the outgoing worker still holds its physical tile lease.
Expired/observed/excess requests are cancelled only within this station owner. New requests are persisted individually with reserved identities; repeat calls/reconstruction recalculate against already saved requests. Inputs and aggregate queue capacity are checked before cancellations. Zero-production queued bodies are discarded rather than consuming a productive slot. Existing population demand remains independent.
Validation: npm run quality passed (107 production files, zero Lizard violations); npm test passed 261 tests in 3.27s. Coverage includes JSON persistence, repeated reconciliation, spawning-name deduplication, exact replacement boundary, scoped safety/excess cancellation, invalid-input preservation and obsolete queued bodies. No engine run for this queue integration. Native rate estimation, station task assignment/staging, colony wiring and engine saturation/replacement evidence remain required.
