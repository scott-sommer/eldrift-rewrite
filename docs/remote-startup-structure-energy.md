# Startup structure energy ledger

ED-29: portable physical stock and standalone spawn-timeline integration; not yet integrated into the project forecast or production admission.

The aggregate spawn pool cannot justify a transfer into one structure using another structure's free capacity. This ledger tracks each declared spawn/extension separately, with outgoing-stock and incoming-capacity reservations as liabilities. A birth debit follows the supplied origin order atomically; insufficient stock or a debit touching reserved stock leaves the ledger unchanged. It does not rearrange native debits to evade reservations. Deposits stop at the chosen structure's unreserved capacity. Births precede transfers within a modeled frame.

The caller supplies the exact charge order. Existing native spawn execution omits energyStructures; pinned engine defaults to owned active spawns sorted by distance, then extensions sorted by distance. Explicit lists use their declared order. The ledger does not infer distance ties or certify that a future native producer supplies the same order.

Checkpoint format 1 binds initial physical facts, reservations and orders. Restore replays bounded events and checks point conservation; structure enumeration order is immaterial, charge order is material. Limits: 128 structures, 16 origins, 8192 events, 1 MiB checkpoint. The ledger owns neither production Memory nor real reservations, actions, queues or cash receipts.

They compare default and explicit spawn debits, atomic insufficient-stock refusal, and partial native transfers. A separate case demonstrates why reservation-aware admission must refuse a native debit that would consume reserved stock. These are processor comparisons, not a full server lifecycle or economic return claim.

## Standalone funding integration

StartupSpawnFunding optionally accepts energyLayout. Its initialEnergy and capacity must exactly equal unreserved layout totals; total physical stock must fit the home bank, every spawn slot needs a charge order, and unaddressed static refill schedules are refused. Admission debits physical stock and financial funding together. Refused charges preserve the slot and money; skip continues to cheaper requests, while wait blocks eligible later requests. The existing pure spawn allocator supplies eligibility, placement and deterministic ordering through a small forecast-owned admission boundary.

Unlocated external expenses reduce the financial accessible budget but do not free physical space at an invented location. Addressed transferHousehold calls require a destination and holder and cap the debit by both actual destination space and available non-spawn bank stock. They remain internal transfers, never income. Snapshotting copies the layout; ordinary checkpoint shape is unchanged, while point-aware standalone checkpoints require an energy member. Older strict timeline readers reject the extra member. Restore binds all charge events to paid birth identity, origin, tick and cost and checks scalar accessible/refill totals against physical event history and elapsed expense schedules. It aggregates scheduled costs between events rather than replaying elapsed frames.

At this intermediate boundary, household and project constructors explicitly refuse energyLayout: their trip addressing, conservation links and persisted version fences still need integration. This prevents silent partial support in the current project format 2/3 and planning version 3. No production Memory version or native action policy changed in this increment.

## Addressed household integration

Household redistribution trips now optionally name a destination. Point-aware households require a known structure for every trip; aggregate households refuse addressed trips. The redistribution capability passes a detached trip to the deposit port, leaving route selection with the caller. Destinations enter the input identity while old unaddressed identities remain unchanged. The endpoint's initial stock excludes all physical structure energy, including reserved energy, to prevent counting another owner's stock twice.

Point-aware household checkpoints use format 2; aggregate households retain format 1. Restore links every physical deposit to its declared trip destination, arrival, paid-worker expiry and completion clock, then reconciles each trip's delivered total. Physical charge/birth links remain the standalone timeline's responsibility. Older household readers refuse format 2. The full project boundary still refuses point-aware inputs until its versioning and planning migrations are updated.

Targeted behavior includes a full spawn refusing cargo despite unused extension capacity, retaining that cargo across JSON reset, and accepting it only after a later paid birth frees space in the addressed spawn. Reassigned deposit history and format downgrades are refused. Blocked cargo expiry is charged once and survives reset. ## Native physical observation and explicit order port

observeNativeStartupEnergy reads current owned, active spawn/extension stock and both stock/capacity quantity liabilities. It reports copied layout facts, unreserved scalar totals, observation tick and policy identity without initializing or publishing state. Missing origins, bounded-layout overflow and claims exceeding current stock/capacity defer. Expired claims do not reduce budgets. This observation does not supply the total home bank or endpoint route/trip schedule; those remain separate owners.

The shared adapter policy spawn-first-range-id-v1 sorts spawns before extensions, then by Chebyshev range from each origin and stable ID. This follows the pinned engine's category/range ordering and deliberately defines equal-range ties. It is an explicit SDK energyStructures policy, not a claim to reproduce unspecified native enumeration ties. createNativeSpawn accepts an optional injected order port; null refuses the call, and supplied structure arrays are copied into SDK options. Existing callers that omit the port retain their previous SDK options. A strategy must inject this policy into actual execution before treating the snapshot's order as its execution contract. Default production composition has not opted in yet.

## Native physical admission

An optional NativeBot spawnEnergyPolicy now wires the explicit policy through application dispatch to structure action preparation. The selected native fixture opts in; ordinary production defaults still omit it. Preparation checks a fresh physical/claim snapshot before scalar intent keys/energy are reserved. Only SDK OK commits the ephemeral physical debit, so accepted calls from multiple origins share the same vector. The existing durable intent owner still retains uncertain/rejected attempts for the tick.

The guard compares durable scalar pending energy with its accepted physical debits. Unknown pending costs (including a recreated guard after a same-tick reset, failed SDK attempt or unrelated renewal) refuse conservatively. Changed facts/claims after an acceptance also refuse rather than dropping pending debits. The next tick starts from actual fresh stock. No additional persistent namespace or reservation owner is introduced.
