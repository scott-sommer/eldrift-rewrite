# Work selection and execution (ED-22)

## Current implementation

`capabilities/work/assessment.ts` defines plain observed facts and work orders. `adapters/screeps/work-assessment.ts` snapshots owned construction, repairable structures and controller state; externally supplied blocked-site/excluded-repair IDs preserve planning/operator boundaries. `features/work` owns small policy, candidate and selection modules. Policy is injected as plain data, not a service locator. The production room feature now composes these with persistent work tasks, the bounded task runner and shared movement/action dispatch. `workersEnabled` opts in; workers must carry population owner `work:<home>` and matching home. Room mode selects builder, fortifier or upgrader behavior. Energy acquisition now uses a persistent collect phase; population creation and recovery remain unfinished.

Builder selection orders controller downgrade emergency, critically damaged ordinary structures, dependency-ready construction, routine repairs, ramparts, walls and ordinary upgrading. Construction types have a configurable priority list. Fortifiers build first, then rank barriers by hits plus distance weight (default20000); builders preserve rampart-before-wall fallback. Upgraders select controller work. Ordinary upgrading can be suppressed by the caller's energy/recovery policy, while downgrade prevention remains available. Builder/fortifier upgrade fallback stops at RCL8; dedicated upgraders can maintain RCL8 when permitted. Current valid targets are retained within the best priority tier, but emergencies preempt lower-priority work.

Repair thresholds, wall/rampart targets, downgrade threshold, distance weight and construction ordering are injectable. Default barrier targets are50000, critical fraction0.2 and routine fraction0.8. Repair targets are capped to native maximum hits. Unowned controllers, hostile structures, excluded barriers, blocked construction, completed work and other-room targets are not selected. The selector does not own resource acquisition, population, hysteresis or role switching. Production tasks approach targets through shared movement, retain identity despite changing scores, and replace expired or superseded work with cleanup. No exclusive target lease is acquired: multiple workers may cooperate on a site/controller.

## Worker collection integration

Work tasks now have work/collect phases. Empty energy enters collect; collection persists until full or until no eligible source remains while the worker has some energy, then resumes useful work. Issued withdrawals do not immediately change the observed cargo, so phase transitions rely on next-tick observations. Blocking does not consume generic retry budgets. The existing100tick task expiry bounds a task; reacquisition after expiry can start with partial carried energy.

Collection is separated into plain source/order types, native observation, pure work source policy, a reusable collection intent reservation wrapper and native transferStep/action/movement execution. Controller links use the existing role classification. Shared logistics stock and receiving-creep capacity pools prevent workers from overbooking resources already claimed by couriers or links. The reservation is written before the native call; issued/uncertain outcomes retain it until the next tick. Rejected/conflicting outcomes release only their own claim. Pickup requires its entire native amount; it is never treated as a quantity-limited withdrawal. These collection intents do not create delivery receipts or claim completion of a courier request.

Current default source ordering is nearby energy drops (>20 within3), controller links, storage above the configured reserve, containers, remains, distant/small drops and terminal fallback. Same-priority targets use distance then ID. No spawn/extension/tower, hostile/inactive store, mineral drop or source link is collected. This is a shared baseline, not exact source parity for every role: legacy builder uses >50 drops and stricter link conditions; upgraderV2 requires a full-capacity controller link and handles Transfer flags; jobs.findResource used by fortifiers prefers storage/terminal and can prefer terminal energy above35000. These profile differences, assigned-miner fallback, bootstrap harvesting and non-energy cargo disposal remain open. The selector takes injected policy values; runtime currently exposes only the storage reserve. No legacy role is marked fully ported by this milestone.

## Worker foreign-cargo disposal
All native worker modes now suspend their own work head when non-energy cargo occupies carry capacity. Disposal uses the existing cargo-recovery request, quantity ledger, transfer journal and native haul behavior; it never books the worker's energy for disposal. After confirmed disposal, work assessment selects the next build/repair/upgrade order afresh. Prior transfer effects settle even if worker execution has been disabled. Unrelated tasks are neither erased nor executed by this cargo path, and an unresolved transfer journal prevents fallback dropping.

Provenance: role.builder.js lines81-82 drops non-energy cargo; role.upgraderV2.js lines29-42 deposits non-energy cargo into room storage. The rewrite deliberately unifies these as store-first disposal, preferring the shared compatible terminal/storage/container destinations. If no destination exists, workerCargoDropFallback=true (default) releases one non-energy resource per tick through the shared action arbiter, retaining the builder's ability to free capacity without storage. Set false to retain cargo and wait. A full task queue or unavailable reservation does not itself authorize dropping when a physical destination remains available. Dropped cargo receives no delivery receipt.

Dismantle shares the primary-work slot with harvest/build/repair. The reusable dismantle step does not require carried energy and leaves target/completion policy to its caller.

Only a bootstrap-owned worker assigned to the owned room is eligible. A depleted natural source remains a harvest/wait target and never triggers salvage.
