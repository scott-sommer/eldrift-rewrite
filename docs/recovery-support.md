# Recovery donor support (ED-22)

## Implemented contracts

Donor policy and shared-store contracts are implemented. The native observation/guard milestone below also exercises actual cross-room transfer and ownership-loss recovery. Main does not yet select/spawn/retire donor missions automatically; ED-22 donor support remains incomplete until that orchestration and its acceptance cases are implemented.

The source references are room.energy.recovery.js:getCourierSupportRequests, spawner.js:queueRecoverySupportCouriers (line503), and role.courierV3.js:runRecoverySupportCourier (line70). Legacy support requests use25000 as a fleet carry-capacity target; couriers then shuttle while the target remains in recovery. That is not a one-time25000delivery receipt or a per-tick withdrawal allowance.

- support-identity assigns one explicit population/request scope per donor-target pair using a JSON-encoded tuple. Parsing rejects foreign home scopes, self-routes and malformed identities. This is separate from normal local hauling and scavenger population ownership.
- support-fleet composes applyCourierDemand and the existing spawn queue. It counts each live unit's actual capacity, each pending body's capacity and spawning identity once. This deliberately corrects legacy code that counts every live/queued courier using the newly planned body profile. Priority2 follows local miners0 and ordinary couriers1. Request expiry, replacement lead time and deterministic surplus pruning remain in the shared demand service. Exit/no usable body/zero target cancel only this route's pending spawns; live creeps remain for the runtime to finish deliveries and return home.
- support-endpoints prefers owned storage withdrawals, then owned terminal withdrawals, while retaining a caller-selected combined energy reserve. Reserve0 reproduces the old unconstrained withdrawal pool; a positive reserve is an explicit policy option, not yet a new runtime default. Target destinations prefer active owned storage, terminal, spawn and extension with actual headroom. Full stores cannot mask a usable fallback, correcting the old storage-first selection that could repeatedly transfer into a full store.
- support-requests composes shared source/sink reconciliation and generateStockRequests in the donor room queue. Each route has a bounded outstanding batch, one new request per reconciliation, and caller-selected lifetime. Confirmed delivery frees batch capacity for another shuttle; it does not retire the whole mission. Local and other-target commitments in that donor queue consume observed source stock before new support requests. Unassigned obsolete requests are cancelled; admitted request reservations protect in-flight delivery across recovery exit. Global sink/stock reservation admission still enforces contention across different donor-room queues.

Reserve-aware source descriptors are planning observations, not bookings. The native integration must apply freshly observed reserve-limited availability both at admission and at each collection attempt. It must not use the unconstrained observeHauling source stock for donor withdrawals after generating a reserve-limited request. A target becoming inactive must also stop new collection admission; merely preserving an admitted request record does not authorize another empty courier to collect its residual quantity.

## Required runtime integration and evidence

1. Resolve each target room's own effective configuration and refresh its recovery assessment before consuming proposals. Share the existing persistent configuration snapshot and recovery evaluator; donor-room settings must not overwrite target-room recovery thresholds. Apply fresh ownership/visibility checks before new admission. Persisted donor proposals are not delivery authorization after ownership loss.
2. Keep fleet recruitment separate from already assigned courier execution. New fleet demand follows the selected donor proposal. An existing support courier may finish carried energy after recovery ends; its empty return-to-home and transition into normal local hauling need explicit ownership handling. Legacy couriers also continue their assigned route while the target is active even if the donor no longer appears in the next proposal snapshot; a configured donor reserve must constrain new withdrawals independently.
3. Feed native store facts through supportSources/supportSinks. Account for actual body capacity when mapping live/spawning units. Wire reserve and body/lifetime/travel settings deliberately. Reuse the shared native transfer journal, quantity ledger, haul task and movement service with a support route policy permitting the legacy16room path limit. Review expiry and replacement lead time for the selected route, rather than using local-room100tick defaults blindly.
4. Local courier admission, pending-work population floors and route sizing now exclude donor-owned requests from the same room queue. Support couriers admit only their own donor-target scope. Generic cargo recovery remains a separate receipt identity and must not falsely credit a failed support shipment.
5. Settle prior-tick effects before retiring a task or changing ownership. Empty stopped couriers return home before joining local logistics. Carried energy should finish an eligible target delivery, choose a valid fallback if that sink fills/disappears, or recover safely at home if target ownership is lost. Releasing a source claim is not proof of delivery. Do not send cargo to newly hostile structures merely because their IDs still resolve.
6. Add packaged two-room native scenarios: actual reserve-bounded withdrawal, cross-room travel and confirmed delivery; repeated shuttles; recovery exit with loaded and empty couriers; home return and normal ownership; target full/lost and donor reserve changes; reset/expiry/death without duplicate claims or receipts. Prove new fleet spawning with actual bodies, not just seeded support units. Existing navigation and local hauling scenarios alone do not close donor support parity.

## Native observations and guarded shared hauling

`support-observation` reads store and sink facts only from currently owned rooms. `native-support-view` combines those facts with supportSources/supportSinks and the ordinary hauling observation. The caller supplies a current donor-reserve lookup. The view clamps source availability to fresh surplus each time it runs; a stale queued shipment cannot authorize unconstrained collection. Target ownership, supported destination type, active status and actual headroom are checked before delivery. Malformed support scopes and non-energy shipments fail closed. Ordinary cargo-recovery requests retain their separate existing behavior and receipt identity.

`createNativeHaulingTask` now accepts an injected observation function, defaulting to its previous observer. Donor admission and task execution use the same guarded view, avoiding a second transfer executor. Both still use the shared quantity ledger, action arbiter, transfer journal and movement service. Normal local courier admission excludes support scopes; their pending-work population floor and route observations exclude those requests as well. Dedicated support requests therefore neither recruit local couriers nor get consumed by them. The generic factory's default behavior remains covered by the existing hauling regressions.
