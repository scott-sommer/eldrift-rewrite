# Shared empire lab production (ED-36)

Ordinary bot composition now supports selectable room-local or shared empire production. Legacy resourceManager.js (baseline f2bbf7e8, setupLabs155+) selects a deficient global target and round-robins intermediate recipes. The rewrite separates global deficit allocation, durable room windows, local dependency planning, lab assignment, shared hauling and actual reaction admission. It proves local funding before assigning a complete final-product window rather than assuming remote stock can fund local effects.

## Configuration and ownership

labProductionScope defaults to 'room', retaining existing direct/per-room chain behavior. Set shared empire labProductionTargets, labReactionsEnabled:true and labProductionScope:'empire' to participate. Room profiles/overrides can select scope and batch/reserve options. Participating rooms must inherit the same target records as shared empire policy; conflicting target overrides refuse explicitly. The coordinator does not edit operator configuration each tick.

The native factory captures recoverable stock from visible owned banks, eligible labs and admitted industry couriers once per tick. Manual exclusions, desired/current-retiring boost roles and actor pins are applied consistently. It reconciles existing windows before proposing new work. Ready rooms need a viable physical topology, no previous assignment and no admitted lab supply; previous local work drains before joining empire allocation. The ordinary reaction feature still owns assignment, reservations, transport generation and native reactions.

## Portable allocation and durable progress

planEmpireProduction accepts up to50 distinct room snapshots,16 priority targets and50 existing commitments with at most one per room. It subtracts observed global product and outstanding final demand once, uses deterministic room/product ordering, and respects shared/per-room search caps. ProductionDependencies funds the entire final window locally, including intermediate floors/reserve gaps, using bounded halving under shortage. Funded final amount and first intermediate step are separate. One assigned room occupies its slot until its previous work settles. Zero-remaining retiring windows occupy a room without inventing reserved demand. This is deterministic feasible allocation, not a throughput/transport-cost optimizer.

Namespace industry-empire-production/empire, owner industry, schema1 persists at most50 windows. Original room/product/amount/context/root ceiling/initial step establish immutable replay identity. Bulk admissions validate the complete candidate before one write; absent reads/empty admissions do not initialize state. Conflicting replay cannot overwrite progress or retiring work. Model, schema, progress, store and coordinator have separate responsibilities.

Positive observed room-total final-stock deltas reduce remaining work; consumption never resurrects credit, repeated observations are idempotent, and partial final progress shrinks execution ceilings. These observations mean stock fulfillment, not manufactured-success counters. Imports can satisfy a window, while actual global stock still determines whether more demand exists. Consistent snapshots must include the same eligible banks/labs/admitted courier pools across internal transfers. Terminal coordination must preserve that accounting boundary before imports/exports are enabled.

Intermediate steps advance after observed completion. Unfundable next steps become null/blocked and retry later. Completed/cancelled/obsolete-context or excess-demand windows retire. Production stops, existing output drains through normal hauling, the assignment retires, and release requires the owning lab's admitted services to settle. Tasks, receipts, quantity claims, journals, boost bindings and actor pins are never cleared to force progress. Switching scope/disablement drains a retained window before local policy resumes.

Missing observations do not imply completion or erase windows. Unseen windows freeze new admissions conservatively; a changed visible participation/context set can retire other windows until settlement. Confirmed loss/vision resolution is qualified below for courier removal; broader evacuation, ownership recapture and mission-death behavior remain open. Local stock alone funds local effects; ED-37 owns future terminal movement and commitments.

## Visibility versus ownership resolution checkpoint

The native adapter now supplies all visible room names separately from its owned production snapshots. A visible controller with my:false confirms ownership loss; absence from Game.rooms does not. Confirmed loss retires the window through the existing coordinator and cancels only unclaimed reaction supply. The release predicate waits for both admitted lab quantity claims and all surviving owned actors whose population home is the lost room. This conservative actor fence persists even after a reservation expires, so live cargo is not treated as gone merely because a lease ended. Once those actors are absent and admitted work is no longer live, the lost window can release and another owned room can receive replacement demand. Unknown visibility never authorizes this release.

Last-known industry assignments, room intel and other feature state are not erased to resolve lost ownership. Captured/unusable resources are excluded from current owned inventory. This is window abandonment after lost ownership, not successful production or cargo recovery. Existing task/journal/death cleanup retains its responsibilities. Surviving-home evacuation/reassignment is not implemented by this helper and can conservatively retain the window; that remaining lifecycle path needs its own policy.

Unit tests distinguish unseen/visible loss, independent claim/actor fences across reset, unclaimed-only request cancellation with unrelated services preserved, retained actual assignment identity, owned-room settlement and coordinator replacement of a released visible nonparticipant. At the loss-distinction checkpoint, packaged native ownership-loss and vision-regain qualification was pending; the bounded cases below now supply that evidence. A follow-up should lose the controller while carrying admitted supply, retain a visible observer from another home, prove the window stays fenced while its courier survives, then observe actual courier death/task cleanup and replacement production elsewhere without manufacturing-success credit for lost cargo. Separately remove/recover vision and prove state retention through reset. Existing ordinary shared-production/policy scenarios are regressions, not substitutes for those tests.

No new schema or configuration key is introduced. Existing empire-window/labProductionScope rollback obligations still apply; do not delete retained assignments or journals to force an older bot to resume.
