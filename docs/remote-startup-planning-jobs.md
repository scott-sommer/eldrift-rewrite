# Persistent startup planning jobs

ED-29 adds `createStartupPlanningJob`, a feature-owned runner around the portable forward simulator. It keeps one scratch candidate per home, separate from durable selected geometry and ordinary workforce/task ownership. The default native bot does not yet register a candidate-planning strategy.

`remoteStartupPlanning/<home>` version1, owner `remotes`, stores the home, revision, monotonic write clock and one nullable job. A job contains remote room/source, assignment generation, caller context binding, original observation tick/expiry, normalized model input and validated format1 checkpoint. The complete record is bounded to262,144 JSON characters, in addition to the model/copier bounds. The input codec preserves ordered bodies and placement while rebuilding the live-name Set. Its canonical wire reuses the existing input identity rather than inventing a second model serialization.

`advance` requires the expected revision, a current tick, maximum frame count and optional frame guard. Zero admission or frame budget makes no write. Completed frames are checkpointed even when the guard refuses the next frame; callers must reserve serialization/publication budget separately. CAS/clock refusal, expiry and capacity are explicit deferred outcomes. Only a successfully persisted complete job returns a completed result. Partial and conflicting work never produce a usable result. Repeated reads of matching completed evidence do not update the clock or initialize state.

Room/source/generation, binding, observation epoch, expiry and normalized input all fence reuse. Changed candidates replace scratch progress and cannot read the previous result. Backwards clocks and expired observations cannot retrieve a completed forecast. Withdrawal matches source/generation and revision, leaving selected evidence, requests and other homes/owners untouched. The caller must freshly derive its context; a stored observation is not current execution authority.

Typed plain-data/checkpoint capacity errors distinguish supported deferral from corrupt state or unrelated failures. Storage reads remain outside that deferral boundary, including a writer that corrupts the record during frame admission. Capacity refusal never evicts an existing candidate or returns a forecast as complete. The job and checkpoint schemas have not changed their wire formats as part of the typed-error addition.

Reads validate/restore bounded state and can be more expensive than reading a small selected-geometry record. Final birth admission must use its existing cheap current policy boundary, not call this planner. Total cross-home memory, serialization CPU and selection-policy integration remain unqualified. This is not a background scheduler, native observation converter, current-worker importer, spawn reservation or profitability policy.

Seventeen new cases cover JSON restart/pending settlements, completion-only publication, read-only reuse, guarded partial progress, context/input invalidation, expiry/backwards clock, concurrent/stale writers, caller mutation, record/input capacity, scoped withdrawal, foreign/future/corrupt state and precise error boundaries. It cannot discard actual spawn/logistics/tasks/journals/claims/confirmed receipts or reinterpret forecast credit as actual cash.
