# Finite startup replacement derivation

ED-29 now derives a next replacement request from a completed, exactly input-bound portable project checkpoint. Restore verifies the original input/checkpoint binding and completion before birth history is used. The strategy appends the earliest next finite service request and returns a detached new input. It does not run an unbudgeted whole-horizon simulation, publish state or enqueue a native body. The producer must reevaluate the changed input through the existing cooperative planner before deriving another extension or presenting the final candidate for comparison.

For the final miner interval and each courier chain leaf, the predecessor's actual forecast activeAt, calibrated1499 active life and retirement allowance establish service end. New request readyAt subtracts exact approach and body spawn duration, so an unconstrained new miner reaches the station when its predecessor stops. Shared spawn contention or unavailable funding may delay that admission; it is never moved earlier using anticipated money. Courier handoffs can overlap returning paid cargo under the existing finite courier model. Only service beginning within the declared horizon is proposed. Stable :next descendants prevent re-extending old parents; identity/name collisions are refused.

The new body retains predecessor owner, ordered parts, selected spawn/exit, priority and service timing. It is charged by the normal allocator/funding/cash timeline on actual forecast admission. No birth flow, zero-cost worker, bank-to-spawn transfer, outside income or additional capital is injected. An unscheduled required service birth defers further extension rather than growing a fictional funded dynasty. Count/wire limits retain the existing64-request/64-miner/16-courier constraints.

The strategy handles generated finite source cohorts. Paid-incumbent replacement needs explicit production templates, since imported initial workers do not carry a prospective spawn owner/priority/placement contract; those inputs defer incumbent-template. Existing incumbent import/evaluation paths remain intact. Automatic whole-horizon generation, household redistribution/other workforce schedules, native same-strategy replacement/lifecycle qualification, runtime configuration/adoption and concurrent multi-room capital remain open. This helper does not narrow those requirements.

A new input invalidates old planner/catalog evidence normally. It is not a new persistence namespace or memory migration. Forecast request identities are modeling labels; actual producers still reserve real identities, retain exclusive source/workforce/claim owners and revalidate current authority, visibility, topology, body and funding at native dispatch. Serialization/restore/publication costs require separate CPU allowance; no pressure/soak or RC claim is made.
