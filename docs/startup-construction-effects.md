# Construction effect foundation (ED-29)

The portable construction calculation preserves the pinned engine 4.3.2 processor's base energy charge before boosted progress. Active opening WORK supplies five base progress per part, clipped by processor-time energy and remaining progress. Boost bonuses include inactive boosted WORK, sort descending, and slice by base progress; final progress floors and clips to the remaining work. Repair shares the neutral WORK profile, validation and bonus ordering while retaining its separate energy calculation.

The SDK adapter captures opening body availability. Damage earlier in native processing is represented by the engine's `_oldHits` convention; forecast callers must retain the opening profile rather than recapture a damaged processor body. Construction permissions, target validity, range and object completion remain caller/physical-world responsibilities, not arithmetic assumptions.

## Physical integration

Construction now participates in the shared energy frame. The opening site and body inventory remain frozen while actors issue intents. Explicit current permission is supplied per attempt; refused attempts consume neither energy nor progress. Ordered settlement uses actual available energy. The first completing builder creates exactly the declared zero-stock container, removes the site from actor observations and preserves its completed record for checkpoint witnesses; later builders spend nothing. Birth IDs are forecast-local aliases derived from site identity, never claims about future native SDK IDs or live action targets.

A newborn container joins the same frame's object postprocessing. Its first countdown is 100 before that tick and 99 after, including an owned room; subsequent recurrence uses the supplied 99/499 rule. A later actor's harvest overflow can enter the new store in the same frame. Earlier overflow remains ground energy. Explicit transfer targets still require an opening-visible store. Recipes retain capacity-pool/room/activity metadata; completed containers can subsequently decay and spill through the existing lifecycle.

Native coherent home capture includes visible construction sites and SDK build profiles. Container recipes use native constants; other structure kinds retain null completion recipes and explicitly refuse forecast building until their birth/passive rules are qualified. The caller must assess current ownership, terrain, obstacles and safety; no opening permission is silently renewed forever. New site creation/removal, controller changes and general household construction are not implemented by this integration.

Home restore validates immutable original site recipes and nondecreasing progress, expands the original physical roster only for declared completed sites, then validates health/container/store metadata and clocks. Sites and birth witnesses survive JSON checkpoints, including the completed-then-destroyed case. The actual shared remote miner selector/task cycle now has a physical build admission adapter; the integration fixture uses it instead of a success-only spy and resumes both incomplete and completed builds before harvest/handoff. Construction effects never become courier receipts or bank cash.
