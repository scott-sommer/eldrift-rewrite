# Household transfers in the full startup project

ED-29's forward project now opts into the paid household timeline with an explicit optional household input. The ordinary path retains its original input identity, format2 project checkpoint and declared-refill behavior. Household projects use format3 and retain one normal spawn timeline plus the household endpoint/cargo/loss metadata; spawn state is not duplicated. The full project routes settled source receipts to the actual modeled endpoint, accounts returned loss flows in both household/source cash ledgers, and frees accepting-sink capacity from physical pickup only after current-frame actions.

Household transport and remote miner/courier work cannot share the same body identity. Initial endpoint energy must fit the occupied quoted accepting endpoint and the separate non-spawn home stock. Pickups cannot retroactively enable a same-frame source unload or birth. Actual spawn occupancy remains independent from funding: the integration fixture has100 energy accessible at13 but admits the courier only at15 after miner incubation. Source delivery and internal redistribution are never counted as two income events.

Format3 restore validates endpoint receipts against settled source receipts, household/source costs, paid-body/cargo state and exact sink capacity: initial free space plus declared external changes plus actual pickups minus accepted source delivery. In-flight cargo and accepting capacity survive JSON reset. The static delivery-only composition refuses household inputs instead of silently ignoring the new strategy.

The existing remoteStartupPlanning/<home> namespace is now version3. Genuine schema1/2 jobs without household metadata migrate through detached reads, preserving checkpoint position, revision and pending receipts; only successful writes store the new envelope. Ordinary format1-to2 checkpoint upgrade remains supported. Schema2 records cannot claim household/format3 semantics, older readers reject the version3 envelope, and new inputs cannot reinterpret old checkpoints. This is not a release migration/rollback rehearsal.

No new namespace or default bot/economic-policy configuration is introduced. remoteStartupSchedules and candidate evidence retain their versions; their existing exact-input binding invalidates changed household policy normally. Rollback must disable planning consumers before discarding incompatible simulation jobs. Real admitted spawn/logistics/task/journal/claim/receipt owners must never be relabeled or removed with forecast state. ED-44 must rehearse this boundary.

Native quoted household routes/trip generation, paid incumbent household templates, complete home workforce schedules, actual native same-strategy lifecycle/cashflow, default runtime adoption, concurrent multi-room capital and aggregate pressure remain open. The native VM probe uses real initial room/body/stock facts plus a declared finite household trip hypothesis; loaded/return durations are not yet native route calibration and modeled income is not actual game income.
